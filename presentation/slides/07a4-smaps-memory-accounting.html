smaps Memory Accounting: RSS, PSS, Shared & Private

Per-VMA stats computed by walking the page table. Each page is classified on two axes.

The Two Axes

              Shared          Private
           (mapped by       (mapped by
           multiple          only this
           processes)        process)
  ┌──────────────────┬──────────────────┐
  │  Shared_Clean    │  Private_Clean   │
  │  (can drop,      │  (can drop,      │
Clean  re-read file)     re-read file)   │
  │                  │                  │
  ├──────────────────┼──────────────────┤
  │  Shared_Dirty    │  Private_Dirty   │
  │  (must write     │  ★ MUST DUMP ★   │
Dirty  back to file)    (only in RAM)    │
  │                  │                  │
  └──────────────────┴──────────────────┘
RSS — Resident Set Size
Total pages in physical RAM for this VMA. Shared pages counted fully in each process → over-counts when many processes share libc, etc.
PSS — Proportional Set Size
Like RSS, but shared pages divided equally. If 10 processes share a 4KB page, each gets 0.4KB in PSS. Gives a fair per-process memory cost.
Size
Virtual size of the VMA (end - start). May be much larger than RSS — pages can be allocated but not yet faulted in, or swapped out.

Concrete Examples

Shared_Clean — libc.so .text
100 processes map /lib/libc.so.6 read-only. The code pages are loaded once into RAM, shared by all. Nobody writes to them → clean. CRIU skips these — just re-mmap the file on restore.
Shared_Dirty — shared mmap file
Two processes mmap(MAP_SHARED) a data file and write to it. Pages are dirty and shared. Rare in typical server workloads.
Private_Clean — freshly loaded .data
A file-backed page loaded by this process but not yet written. Could be a read-only config file mapping. Can be reclaimed and re-read.
Private_Dirty — heap, stack, modified data ★
This is where all the action is for CRIU. Valkey's 100GB dataset lives here — anonymous heap pages that exist only in RAM. Every single one must be captured and transferred.
