COW Dump: Primary-Side Unmap Handling

Analysis of correctness when the source process unmaps memory during Phase 2, and whether the primary should listen for UFFD_EVENT_REMOVE.

Current Design

The primary requests UFFD_FEATURE_WP_ASYNC plus UFFD_FEATURE_EVENT_UNMAP and UFFD_FEATURE_EVENT_REMOVE. Detection of unmapped regions uses two complementary mechanisms:

  1. UFFD events: A background thread reads UFFD_EVENT_UNMAP and UFFD_EVENT_REMOVE during Phase 2
  2. EFAULT fallback: process_vm_readv returns EFAULT when bulk transfer hits an unmapped range

Both mechanisms record unmapped ranges for Phase 3 remap detection:

The Breaking Scenario: Address Reuse

The design breaks when the source process does munmap followed by mmap at the same address with unwritten pages:

// During Phase 2 (process running with WP_ASYNC tracking)
munmap(addr, len);                         // removes tracked VMA
mmap(addr, len, PROT_READ|PROT_WRITE,      // new VMA at same address
     MAP_PRIVATE|MAP_ANON|MAP_FIXED, -1, 0);
// Some pages written, some left as zero-fill-on-demand

Data flow showing the bug

  1. Phase 1: VMA [A, B) tracked, all pages sent during bulk (content = C1)
  2. Phase 2: Process does munmap([A, B)) then mmap([A, B), MAP_FIXED) — new content C2, but some pages never written (zero-fill-on-demand, no PTE)
  3. Replica: Receives UFFD_EVENT_REMOVE for [A, B) → clears stale C1 from batch buffer
  4. Phase 3: cow_detect_new_vmas() calls cow_region_subtract([A, B))
    • [A, B) is in tracked_vmas from Phase 1 → no gap detected
    • New VMA NOT flagged as new, NOT added to new-VMA send path
  5. Frozen scan: PAGEMAP_SCAN with PAGE_IS_WRITTEN on original lazy VMA range
    • Written pages → found, sent to replica (correct)
    • Unwritten zero-fill pages → no PTE, not found, not sent
  6. Result: Replica has no data for unwritten pages in [A, B). Batch buffer was cleared by REMOVE event. Drain installs nothing for those pages. Restored process accesses them → SIGBUS
munmap + mmap at same address with unwritten pages: DATA LOSS / SIGBUS cow_region_subtract() compares address ranges only — it cannot distinguish "same VMA still here" from "different VMA at same address." Zero-fill-on-demand pages in the new mapping are invisible to PAGEMAP_SCAN.

Root Cause

cow_region_subtract() (cow-dump.c:570-652) uses address-only comparison. It walks tracked_vmas from Phase 1 and reports gaps. If a new VMA occupies the same address range as an old tracked VMA, there is no gap, and it is not detected as new.

Why the existing test passes

cow_dump_munmap_reuse.c fills every page of the remapped region with 0xBB immediately after remapping. Every page gets a PTE + PAGE_IS_WRITTEN flag. The frozen scan finds them all. The bug only manifests when pages are not written before freeze.

Should the Primary Listen to REMOVE/UNMAP Events?

Yes — events + EFAULT fallback + Phase 3 check together solve the problem While a single REMOVE/UNMAP event doesn't tell us about subsequent mmap at the same address, recording all unmapped ranges allows Phase 3 to detect remaps by checking if a VMA now exists at a previously-unmapped address.

Why this approach works:

  • Immediate detection: UFFD events arrive as soon as unmap happens — no waiting for bulk transfer to reach that range
  • Fallback coverage: EFAULT from process_vm_readv catches any unmaps missed by events
  • Remap detection: Phase 3 checks recorded unmapped ranges against current VMA list — if VMA exists at unmapped address, it's a remap
  • No freeze overhead: Events are processed during Phase 2 — no extra scanning during Phase 3 freeze

Kernel Requirements for UFFD Events

To receive UFFD_EVENT_UNMAP and UFFD_EVENT_REMOVE, the following must be true:

  1. VMA must be registered with uffd (vm_userfaultfd_ctx.ctx != NULL) — ✓ We do this in Phase 1
  2. UFFD_FEATURE_EVENT_UNMAP must be requested at UFFDIO_API time
  3. UFFD_FEATURE_EVENT_REMOVE must be requested for MADV_DONTNEED events
/* cow-dump.c: Enable event features alongside WP_ASYNC */
args->uffd_features = UFFD_FEATURE_WP_ASYNC |
                      UFFD_FEATURE_EVENT_UNMAP |
                      UFFD_FEATURE_EVENT_REMOVE;

Why Traditional VMA Attributes Fail

The initial instinct is to compare VMA metadata (flags, inode, dev, pgoff) between Phase 1 and Phase 3. This works for some cases but completely fails for the hardest scenario:

Chosen Approach: UFFD Events + EFAULT Fallback

Why PAGE_IS_WPALLOWED Was Rejected

An alternative approach using PAGE_IS_WPALLOWED (PAGEMAP_SCAN probe to detect VMA registration loss) was considered but rejected:

  • Adds freeze overhead: Requires extra PAGEMAP_SCAN during Phase 3 freeze — increases downtime
  • Kernel reliability issues: Testing on kernel 6.17 showed unexpected behavior with the probe
  • Feature dependency: For anonymous VMAs, PAGE_IS_WPALLOWED requires WP_UNPOPULATED feature to be reliable

How the UFFD Events + EFAULT approach works

  1. Phase 1: Enable UFFD_FEATURE_EVENT_UNMAP | EVENT_REMOVE alongside WP_ASYNC
  2. Phase 2 (background): Event reader thread polls uffd fd, records unmapped ranges from UFFD_EVENT_UNMAP/REMOVE
  3. Phase 2 (bulk transfer): If process_vm_readv returns EFAULT, record unmapped range (fallback)
  4. Phase 3: For each recorded unmapped range, check if a VMA now exists at that address
  5. Remap detected: If VMA exists → treat as "new" → full process_vm_readv of all pages
  6. Truly unmapped: If no VMA → send PS_IOV_UNMAP_NOTIFY to replica for cleanup

UFFD Events + EFAULT is 100% correct for all scenarios with no freeze overhead Events arrive during Phase 2 while the process runs. Phase 3 only does a simple VMA list check — no extra PAGEMAP_SCAN. EFAULT fallback ensures coverage even if events are delayed or missed.

Key Advantage: No Freeze Overhead

Unlike the WPALLOWED probe approach, UFFD events are processed during Phase 2 while the process continues running. Phase 3 only needs to:

  1. Stop the event reader thread (set phase3_started flag)
  2. Walk the recorded unmapped ranges array
  3. For each range, check if VMA exists in the current VMA list (already parsed for other reasons)

This is O(unmapped_ranges × VMAs), with both counts typically small. No extra kernel calls during the critical freeze window.

Implementation Design

Chosen Approach: UFFD Events + EFAULT Fallback

During Phase 2, a background thread reads UFFD events while bulk transfer uses EFAULT as fallback. Phase 3 checks recorded unmapped ranges against current VMAs to detect remaps.

+ 100% correct for ALL scenarios including anon-to-anon

+ Zero freeze overhead (events processed during Phase 2)

+ Immediate detection (events arrive when unmap happens)

+ EFAULT fallback ensures coverage if events delayed

+ Notifies replica to clean up buffer/RSS for unmapped ranges

1. Enable UFFD Event Features

/* cow-dump.c: Request event features at UFFDIO_API time */
args->uffd_features = UFFD_FEATURE_WP_ASYNC |
                      UFFD_FEATURE_EVENT_UNMAP |
                      UFFD_FEATURE_EVENT_REMOVE;

2. UFFD Event Reader Thread

/*
 * cow_uffd_event_reader - Read UFFD events during Phase 2
 *
 * Runs in background while bulk transfer is active. Reads UFFD_EVENT_UNMAP
 * and UFFD_EVENT_REMOVE events, recording unmapped ranges.
 *
 * Thread exits when Phase 3 starts (signaled via atomic flag).
 */
static void *cow_uffd_event_reader(void *arg)
{
    struct cow_dump_info *cdi = arg;
    struct uffd_msg msg;
    ssize_t n;

    while (!atomic_load(&cdi->phase3_started)) {
        struct pollfd pfd = { .fd = cdi->uffd, .events = POLLIN };
        int ret = poll(&pfd, 1, 100 /* ms */);

        if (ret <= 0)
            continue;

        n = read(cdi->uffd, &msg, sizeof(msg));
        if (n != sizeof(msg))
            continue;

        if (msg.event == UFFD_EVENT_UNMAP ||
            msg.event == UFFD_EVENT_REMOVE) {
            unsigned long start = msg.arg.remove.start;
            unsigned long end = msg.arg.remove.end;

            pr_info("UFFD EVENT: %s 0x%lx-0x%lx\n",
                    msg.event == UFFD_EVENT_UNMAP ? "UNMAP" : "REMOVE",
                    start, end);

            cow_record_unmapped_range(start, end - start);
        }
    }

    return NULL;
}

3. Unmapped Range Recording (Thread-Safe)

/*
 * cow_record_unmapped_range - Record a range that was unmapped
 *
 * Called from event reader thread OR bulk sender (on EFAULT).
 * Thread-safe (multiple callers may run in parallel).
 */
void cow_record_unmapped_range(unsigned long start, unsigned long len)
{
    struct cow_dump_info *cdi = g_cow_info;

    pthread_mutex_lock(&cdi->unmapped_lock);

    /* Grow array if needed */
    if (cdi->nr_unmapped_ranges >= cdi->unmapped_capacity) {
        unsigned int new_cap = cdi->unmapped_capacity ?
                               cdi->unmapped_capacity * 2 : 16;
        cdi->unmapped_ranges = xrealloc(cdi->unmapped_ranges,
                                        new_cap * sizeof(*cdi->unmapped_ranges));
        cdi->unmapped_capacity = new_cap;
    }

    cdi->unmapped_ranges[cdi->nr_unmapped_ranges].start = start;
    cdi->unmapped_ranges[cdi->nr_unmapped_ranges].end = start + len;
    cdi->nr_unmapped_ranges++;

    pthread_mutex_unlock(&cdi->unmapped_lock);
}

4. Phase 3: Check Unmapped Ranges for Remaps

/* In cow_detect_new_vmas(), after existing gap detection: */
for (i = 0; i < cdi->nr_unmapped_ranges; i++) {
    unsigned long u_start = cdi->unmapped_ranges[i].start;
    unsigned long u_end = cdi->unmapped_ranges[i].end;
    bool has_new_vma = false;

    /* Check if any current VMA overlaps this unmapped range */
    list_for_each_entry(vma, &vmas->h, list) {
        if (!cow_is_vma_trackable(vma))
            continue;
        if (vma->e->start < u_end && vma->e->end > u_start) {
            has_new_vma = true;
            break;
        }
    }

    if (has_new_vma) {
        /* Remap detected - add to new_ranges for full resend */
        add_range(&ranges, &nr_ranges, &capacity, u_start, u_end - u_start);
        pr_err("COW REMAP: 0x%lx-0x%lx unmapped then new VMA appeared\n",
               u_start, u_end);
    } else {
        /* Truly unmapped - notify replica to clean up */
        cow_send_unmap_notification(u_start, u_end - u_start, false);
    }
}

5. Replica Notification Protocol

/* page-xfer.h: New message type */
#define PS_IOV_UNMAP_NOTIFY  11  /* Range was unmapped on primary */

/* cow_send_unmap_notification - Tell replica a range was unmapped
 *
 * Replica will:
 * - Remove pages from buffer
 * - MADV_DONTNEED if pages were already applied
 * - Update lazy IOV list
 */
void cow_send_unmap_notification(unsigned long start, unsigned long len,
                                 bool has_new_vma);

What Happens to Detected Remapped Ranges

Ranges flagged as remapped enter the existing "new VMA" path:

  1. cow_extend_tracked_vmas() adds them to the tracked list
  2. add_lazy_vma_for_new_region() adds them to global_lazy_vmas
  3. The sender does a full process_vm_readv of all pages — not relying on PAGE_IS_WRITTEN
  4. Zero-fill pages are read as zeros and sent to the replica
  5. Replica receives correct content for the entire remapped range

Replica Handling of PS_IOV_UNMAP_NOTIFY

/*
 * cow_handle_unmap_notification - Handle unmap notification from primary
 *
 * Reuses existing infrastructure for cleanup.
 */
void cow_handle_unmap_notification(unsigned long start, unsigned long len,
                                   bool has_new_vma)
{
    /* Remove from buffer if pages were received */
    cow_page_buffer_remove_range(start, len);

    /* Mark as unmapped in state tracker */
    page_state_mark_range_unmapped(start, len);

    /* Release RSS if pages were already applied */
    if (pages_were_applied(start, len)) {
        cow_release_unmapped_pages(restored_pid, start, len);
    }

    /* Remove from lazy IOV list */
    cow_remove_lazy_iov_range(start, len);

    if (has_new_vma) {
        /* Re-add to IOV list - will receive new content */
        cow_add_lazy_iov_range(start, len);
    }

    /*
     * TODO: Ask CRIU maintainers if VMA mismatch is acceptable.
     *
     * When primary unmaps without remapping, the replica's restored
     * process still has the VMA (from Phase 1 dump). We release pages
     * via MADV_DONTNEED but don't remove the VMA itself.
     *
     * Options if this is problematic:
     * 1. Inject munmap via ptrace/compel after restore unfreezes
     * 2. Update image files before restore to remove VMA entry
     * 3. Accept the mismatch (current approach)
     */
}

Practical Risk Assessment

FactorAssessment
How common is munmap+mmap at same address? Rare in most workloads. Happens in custom allocators (jemalloc arena recycling), JIT compilers, and some database engines.
How common are unwritten pages after remap? Common if the allocator reserves large regions but fills lazily (e.g., arena-based allocators that mmap large then write incrementally).
Existing test coverage cow_dump_munmap_reuse.c covers the written case. No test for unwritten pages after reuse.
Failure mode without fix SIGBUS on restored process when accessing the missing pages — hard crash, not silent corruption.
Mitigation by replica UFFD_EVENT_REMOVE clears stale data, preventing wrong-content-served. But doesn't provide new content either.
Performance impact of fix One PAGEMAP_SCAN ioctl per tracked VMA during Phase 3 (frozen). Each probe walks ≤1 PTE. For 1000 VMAs → ~1000 ioctls → sub-millisecond total.
