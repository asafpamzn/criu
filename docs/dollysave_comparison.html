A new SAVE path for Valkey — Tenets & Comparison

This document proposes the tenets we should use to evaluate any full-sync / SAVE mechanism for Valkey, and compares the three candidates — BGSave (the current fork-based path), ThreadSave (proposed in #2878), and DollySave (proposed in #3609) — against those tenets.

Tenets — How we choose the best full sync method

Listed in priority order. If two methods tie on a higher tenet, the next one breaks the tie.

  1. Cost — Memory & CPU.
    • Memory: Memory is the largest cost contributor for an in-memory database. The SAVE path must not require reserving headroom that grows with the write rate (no copy-on-write amplification).
    • CPU: As more cores are dedicated to steady-state request processing (io-threads, future high-TPS targets), an infrequent operation like SAVE should not pin cores or steal cycles from the request path.
  2. Minimize customer-visible latency and downtime.
    • The best SAVE is one the customer doesn't notice.
    • Minimal p50 and p99 impact while SAVE runs, and minimal process-freeze time — across all workloads, including pipelined clients, multi-key commands, and large objects.
  3. Robustness.
    • Must work reliably across all workloads, data types, and modules (including VSS / vector indexes, Streams, large complex objects).
    • Must not OOM the host under heavy write traffic.
    • Must not require fall-through to a different mechanism for whole-DB module aux-data.
  4. Speed of sync.
    • Faster SAVE → shorter replica unavailability, smaller availability / data-loss window, faster scale-up and replica recovery.

How DollySave addresses each tenet

Tenet Mechanism
1. Cost — Memory No fork(), no COW. Dirty pages are tracked by the kernel via UFFD_FEATURE_WP_ASYNC and read in bulk via PAGEMAP_SCAN — no page duplication, no userspace fault handler.
1. Cost — CPU No object serialization on the main thread. Memory is streamed raw; compression runs on parallel workers off the request path.
2. Latency & downtime Bulk transfer happens while the process runs. Only a brief final freeze captures last-moment dirty pages. No per-key locking, no head-of-line blocking, no special path for large objects or modules.
3. Robustness Constant memory → cannot OOM. Large complex objects, multi-GB module aux-data (VSS, search indexes), multi-key commands, EVAL, MIGRATE, and pipelines are all handled the same way: they are just memory. CRIU restores threads, mutexes, file descriptors, sockets, and signal handlers.
4. Speed Streams raw memory, skips RDB encoding entirely. Wins hold even single-threaded on a small instance — confirming the speedup is not just from parallelism.

DollySave limitations

  • Cross-version sync: DollySave transfers a live process image, so primary and replica must run identical binaries and kernel versions. Version upgrades need a two-phase workflow (DollySave to a same-version intermediate node, then a standard sync to the upgraded target).
  • Kernel floor: Linux ≥ 6.7. Older kernels and non-Linux platforms still need BGSave or ThreadSave as a fallback.
  • RDB-format snapshots: DollySave produces a process image, not RDB. Existing RDB-export workflows need either eager (background) or lazy (on-restore) conversion.

Note on multithreaded BGSave

Multithreaded BGSave could make it faster and reduce OOM risk, but it would require ~6× more CPU than DollySave to achieve comparable speed. Those threads would compete with io-threads for resources, or require customers to reserve 6× spare cores for an infrequent operation.

Summary

DollySave + UPGRADE should cover most workflows. BGSave remains available as a fallback for older kernels and non-Linux platforms.
