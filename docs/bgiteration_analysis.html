1. Consistency Model

Epoch/Version Mechanism

Iterator Creation: server.amz.iterator_epoch++ → it->consistent_modification_id = epoch_at_creation Key Modification (amzSignalModifiedKey): de->metadata->iterator_epoch = server.amz.iterator_epoch (current global epoch) During Iteration (feedIterator): if (de->metadata->iterator_epoch > it->consistent_modification_id) → SKIP (key was modified AFTER snapshot started)
Point-in-Time Without Fork

Uses a monotonically increasing uint32_t epoch. Each key is stamped on modification. The iterator skips any key whose epoch exceeds the snapshot's creation epoch. This provides a logical point-in-time view without physical memory isolation.

WARNINGEpoch Wraparound Risk

The epoch is uint32_t (4 billion values). At 1M writes/sec, wraps in ~72 minutes. A long-running snapshot under extreme write load could theoretically see a wrapped epoch and include post-snapshot keys. Unlikely in practice but not impossible.

Clone Optimization

Small String Cloning Avoids Blocking

tryCloneDbEntry() clones small strings (RAW/EMBSTR encoding, not spilled to flash) if:

  • Item size ≤ bgiteration_max_item_clone_size
  • Total clone pool ≤ bgiteration_max_clone_pool_size

When cloned, the client is NOT blocked — the BG thread works on the copy.

CRITICALClone Limited to Strings Only

Only OBJ_STRING with RAW/EMBSTR encoding can be cloned. Hashes, Sets, Sorted Sets, Lists, and Streams always block. A TODO in the code acknowledges this gap. Large collections (e.g., a 1M-member sorted set) will block the client for the entire serialization duration.

3. Multi-Key Commands (MSET, SUNIONSTORE, etc.)

FIRSTKEY_MOD Optimization

Commands flagged with REDIS_AMZ_CMD_FIRSTKEY_MOD (flag '1') indicate that only the first key is modified; remaining keys are read-only sources. This allows the system to skip expediting read-only keys when replication is disabled.

MSET Deep Dive

PERF CONCERNMSET Blocks on ALL Keys

MSET does NOT have FIRSTKEY_MOD because it modifies ALL keys. With N keys:

  • Consistent mode: All N keys that haven't been iterated are expedited. Client blocked until BG thread processes all non-cloneable ones.
  • Non-consistent + repl: If ANY of the N keys has been iterated, ALL remaining keys are expedited.
  • Non-consistent, no repl: Only blocks on keys currently in-use by BG thread.

A MSET with 100 keys where 50 are in-use could block for 50× single-key serialization time.

SUNIONSTORE Deep Dive

OPTIMIZEDSUNIONSTORE Only Blocks on Destination (Without Replication)

SUNIONSTORE has FIRSTKEY_MOD. The optimization at line 1115:

  • When BGITERATOR_FLAG_REPLICATION is NOT set: numKeys = 1 — only the destination key is checked for blocking.
  • When BGITERATOR_FLAG_REPLICATION IS set: ALL keys (dest + sources) are checked because the replica needs source values to replay the command.
WARNINGSUNIONSTORE with Replication: Source Keys May Block Unnecessarily

With replication enabled, if the destination key has already been iterated but source keys haven't, ALL source keys are expedited and the client blocks. This is correct for replication consistency (the replica needs the source values) but creates potentially large blocking windows when source sets are large collections.

Boundary Spanning Logic

Command: SUNIONSTORE dest src1 src2 Case A: All keys FUTURE (not yet iterated) → No expedite, no block, no replication → Iterator will naturally encounter all keys Case B: dest=PAST, src1=FUTURE, src2=FUTURE (with REPL) → src1 and src2 are expedited (sent to BG thread now) → Client blocked until BG processes src1 & src2 → Command IS replicated to stream Case C: dest=FUTURE, src1=PAST (with REPL) → dest is expedited → Client blocked until BG processes dest → Command IS replicated Case D: All keys PAST → No block needed → Command IS replicated
