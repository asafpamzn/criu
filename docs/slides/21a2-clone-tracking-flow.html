Bulk Transfer Phase

How pages are read
8 parallel worker threads, each reading contiguous chunks of VMAs via process_vm_readv(). Pages are LZ4-compressed and sent over TCP to the replica's page-recv process.
Concurrent write tracking
While bulk transfer runs, the CLONE monitor thread handles WP faults. Each first-write to a page marks it in the dirty_bitmap. These pages will be re-sent during convergence.

Convergence Phase

Fork snapshot
CRIU calls fork() on the source process (via ptrace). The child gets a CLONE copy of all pages — a temporally consistent snapshot. Reads from the child see the exact state at fork time.
Only dirty pages re-sent
Only pages in the dirty_bitmap (WP-faulted during bulk) need re-sending. For Valkey at 100K ops/s, this is typically ~2-5% of pages. Convergence completes in seconds.
Cutover: 1ms
After convergence, the replica has all pages. Cutover is just a TCP connection handoff — ~1ms. The source was never frozen during transfer.
