⚠ NOT Re-captured After Early Resume

In COW WP_ASYNC mode, the source process is alive and running after the ~51ms dump freeze. All non-memory state below is captured once at dump time and never re-synced at convergence. This is a known limitation of the current implementation.

⚠ Threads
Source can pthread_create() / pthread_exit() at any time (bio threads, module threads). New threads won't exist in the image. Dead threads still in image.
⚠ File Descriptors
open(), close(), dup2(), accept() all happen during normal operation. FD table drained once via parasite — new FDs not captured, closed FDs still in image.
⚠ Signal Handlers & Pending Signals
sigaction() can change handlers. New signals arrive and queue. PTRACE_PEEKSIGINFO + parasite rt_sigaction only done at dump time.
⚠ Timers
setitimer(), timer_create(), timer_settime() — all mutable at runtime. Values captured once via parasite.
⚠ Thread Register State (IP, SP, GPRs)
After resume, threads keep executing — registers diverge immediately. Signal delivery pushes frames onto the stack and changes IP/SP. Stack pages are re-synced via dirty tracking, but registers are NOT. Creates register↔memory inconsistency.
⚠ Credentials, rlimits, cgroups
setrlimit(), cgroup migration, capability changes — all possible at runtime. Not re-read at convergence.
⚠ Filesystem context
chdir(), chroot(), umask() — all mutable. Captured once.
Bottom line: For a complete general-purpose solution, convergence would need a second dump_one_task-like pass to re-capture all non-memory state — the same way pre_dump (memory only) is followed by dump (everything). The current implementation handles memory convergence only.
