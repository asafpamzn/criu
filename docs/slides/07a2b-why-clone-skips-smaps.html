Why CLONE Doesn't Need smaps

Three Things CLONE Doesn't Need

① No dirty-page accounting
CLONE mode uses userfaultfd write-protect (UFFD-WP) to track writes in real-time. Every first write triggers a WP fault → CRIU snapshots the page. No need for kernel's dirty-page stats.
② VmFlags derived from filename
The critical flag is MAP_GROWSDOWN (stack). CLONE uses set_maps_derived_flags() to detect it from the [stack] filename in maps output — no VmFlags line needed.
③ All pages transferred anyway
CLONE dump sends all pages (bulk transfer), then converges on dirty pages. It doesn't need per-VMA RSS/PSS to decide what to transfer.

What about the missing VmFlags?

Derivable from maps output
[stack] → MAP_GROWSDOWN
[vdso] → VMA_AREA_VDSO
[vvar] → VMA_AREA_VVAR
permissions rwxp → PROT_* flags
Not needed for CLONE
madvise flags (hg, nh, mg, etc.) — the restored process will set these itself.
MAP_LOCKED — not needed during migration, process re-mlocks on startup.
Memory accounting — not needed, all pages sent.
Result: For 200GB Valkey, parsing maps takes <1ms vs smaps taking 2-5 seconds. This alone saves most of the freeze time.
