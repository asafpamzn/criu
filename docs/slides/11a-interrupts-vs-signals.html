Interrupts vs Signals — Why CRIU Only Saves Signals

Hardware Interrupts

What they are
Electrical events from hardware: timer tick, disk I/O complete, network packet arrived, keyboard keypress. The CPU stops what it's doing and jumps to a kernel interrupt handler.
Who handles them
The kernel — always. Interrupt handlers run in kernel space with no process context. The interrupted process is simply paused and resumed — it never knows it happened.
Visible to process?
No. Completely transparent. There is no per-process interrupt state. Nothing to checkpoint.
CPU executing process code
        ↓
[INTERRUPT] ← hardware signal (e.g. NIC)
        ↓
Kernel interrupt handler runs
(process is paused, unaware)
        ↓
Handler finishes → CPU resumes process
(process never knew)

Software Signals

What they are
Software notifications from kernel→process or process→process: SIGTERM, SIGKILL, SIGSEGV, SIGCHLD, SIGUSR1. The process can register custom handlers via sigaction().
Who handles them
The process itself — in user space. Each signal has a disposition: default action, ignore, or custom handler function. This is per-process state that CRIU must save.
What CRIU saves
1. Signal handlers — the table of 64 dispositions (sigaction structs) via parasite
2. Pending queues — signals sent but not yet delivered, via PTRACE_PEEKSIGINFO
3. Signal mask — which signals are blocked, per-thread 
Another process: kill(pid, SIGTERM)
        ↓
Kernel queues signal for target process
        ↓
When process is scheduled:
  → runs registered handler (or default)
  → handler address, flags, mask = STATE
        ↓
CRIU saves this state ✓
Key insight: Hardware interrupt effects that matter to processes are always mediated through higher-level abstractions that CRIU does save: disk I/O → file descriptor state, network packet → socket buffers (TCP repair), timer tick → POSIX timers/itimers. Interrupts themselves are transient kernel events — no per-process state to checkpoint.
