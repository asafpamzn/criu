Pre-dump: What Happens During the Freeze

The process is FROZEN for the entire duration of this pipeline.

① PTRACE_SEIZE
Freeze all threads
→
② collect_mappings
Parse /proc/PID/smaps
→
③ parasite_infect
Inject code blob
→
④ SCAN PAGEMAP ★
The expensive part
→
⑤ drain_pages
Read pages via parasite
→
⑥ clear_refs
Reset dirty bits
→
⑦ UNFREEZE
compel_cure + resume

The Call Chain

pre_dump_one_task()
  collect_mappings(pid, &vmas, NULL)
  parasite_infect_seized(pid, item, &vmas)
  parasite_dump_pages_seized(item, &vmas, &mdc, ctl)
    __parasite_dump_pages_seized()
      pmc_init()           // open /proc/PID/pagemap
      for each VMA:
        generate_vma_iovs()
          pmc_get_map()    // ★ read pagemap into cache
          generate_iovs()  // ★ page-by-page loop
      drain_pages()        // read page contents
      task_reset_dirty_track() // write "4" to clear_refs
  compel_cure_remote()     // remove parasite, unfreeze

Why the freeze is long

Step ④ dominates
For a 200GB Valkey: 52 million pages. Even with PAGEMAP_SCAN, the kernel must walk page tables for the entire address space. On first pre-dump (no baseline), ALL pages are dirty → all 52M must be classified.
Step ⑤ depends on mode
SPLICE mode: drain_pages() uses the parasite's vmsplice(SPLICE_F_GIFT) to move page frames into pipe buffers (zero-copy PTE transfer, not memcpy). READ mode: drain_pages() is skipped entirely — only iovecs (addresses) are recorded. Actual page contents are read after unfreeze via process_vm_readv().
Result: multi-second freeze
For 200GB: pagemap scan ≈ 2-5s, drain ≈ varies. The process is completely unresponsive the entire time. Unacceptable for production Valkey.
