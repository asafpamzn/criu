FD Types: What Gets Saved?

Regular Files (regfile)
Saved: file path, position (lseek offset), flags (O_APPEND, O_NONBLOCK…), mnt_id, fd_flags (O_CLOEXEC), file owner (F_SETOWN)

NOT saved: file content — assumed to exist on the destination filesystem at the same path. If the file moved, restore fails.

Source: files-reg.c
Pipes (pipe)
Saved: pipe ID (links read + write ends across processes), flags, buffered data still in the pipe

How: CRIU reads pending data from the pipe via splice() into a temporary buffer, saves it to image. On restore, creates new pipe, writes data back, then distributes FDs.

Pair linking: read-end and write-end share the same pipe ID — restored as one pipe2() call.

Source: pipes.c
FIFOs (named pipes)
Saved: filesystem path, flags, buffered data

Difference from pipes: FIFOs have a path on disk (e.g., /tmp/myfifo). On restore, CRIU re-opens the path with the same flags. The FIFO file must exist on the destination.

Source: fifo.c
eventfd / signalfd / timerfd
eventfd: counter value + flags (EFD_SEMAPHORE, EFD_NONBLOCK)
signalfd: signal mask (which signals are watched)
timerfd: clock ID, set-time flags, current value + interval

All from /proc/PID/fdinfo/N — kernel exposes type-specific fields there.

Source: eventfd.c, signalfd.c, timerfd.c
epoll / inotify / fanotify
epoll: list of watched FDs + events + data for each (tfd: lines in fdinfo)
inotify: watch descriptors — each with inode, sdev, mask, file handle
fanotify: flags, event-flags, marks (inode or mount marks with file handles)

These are FD-watching FDs — they reference other FDs, creating dependencies resolved during restore.

Source: eventpoll.c, fsnotify.c
TTYs / memfd / BPF maps / pidfd
TTY: terminal settings (termios), session/pgrp, window size
memfd: name, seals (F_SEAL_*), full content (anonymous file in RAM)
BPF map: map type, key/value sizes, max entries, flags, data
pidfd: target PID, inode (reference to another process)

Source: tty.c, memfd.c, bpfmap.c, pidfd.c
