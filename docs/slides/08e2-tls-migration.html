What CRIU dumps for a TLS connection
1. TCP layer (kernel) → TCP_REPAIR: seq/ack numbers, send/receive queues containing encrypted bytes
2. TLS layer (userspace) → memory pages: OpenSSL's SSL_CTX, SSL structs, AES-GCM keys, HMAC state, read/write buffers

CRIU doesn't know about TLS — it just dumps all memory. The TLS state comes along for free.

Does TLS Survive Migration?

With floating IP: YES ✅
Same IP on new machine → TCP connection continues → encrypted bytes flow → OpenSSL context intact in memory → TLS session resumes seamlessly.

Client sees a ~50ms pause. No TLS renegotiation. No certificate exchange. Encrypted data stream continues mid-byte.
With IP change: NO ❌ (reconnect)
TCP connection breaks → TLS session breaks → client must:
1. Detect connection error
2. Connect to new IP
3. Full TLS handshake (certificate exchange, key agreement)
4. Re-authenticate with the application
TLS Session Tickets (optimization)
Even if reconnecting, TLS session tickets help:
• Server's session ticket keys are in CRIU-captured memory ✅
• Client presents the ticket on reconnect
• Abbreviated handshake: skip expensive RSA/ECDH key exchange
• ~1 RTT instead of 2 RTTs for the handshake
Bottom line: Use a floating IP and TLS connections migrate transparently. No client changes, no renegotiation, no certificate dance.
