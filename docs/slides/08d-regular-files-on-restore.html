How CRIU Handles Regular Files (e.g. Log Files)

CRIU saves the file descriptor metadata, NOT the file contents.

What CRIU Saves (Dump)

Per regular file FD
File path — /var/log/app.log
File offset — e.g. 50KB (where the cursor is)
Open flags — O_WRONLY | O_APPEND | O_CREAT
File mode — permissions (0644)
File locks — flock/fcntl if any

NOT saved: file contents, directory entries, filesystem state

What CRIU Does on Restore

// Simplified restore logic:
fd = open("/var/log/app.log",
          saved_flags);   // O_WRONLY|O_APPEND
lseek(fd, saved_offset);  // seek to 50KB
// → process resumes writing
The file must exist at the same path on the destination. CRIU does not create or copy file contents.

Offset Mismatch: The Log File Problem

Source log at 50KB, replica log already at 100KB:

O_APPEND mode ✅ (most log files)
CRIU restores offset=50KB, but O_APPEND always seeks to end before each write. Process writes at 100KB (end of file).
Safe — offset is effectively ignored for writes.
Regular write mode ❌ (no O_APPEND)
CRIU restores offset=50KB. Process writes at 50KB, overwriting existing content in the 50KB–100KB range.
Data corruption if the file diverged.
Typical migration pattern ✅
Replica starts fresh from CRIU restore — no pre-existing log file. Either:
• Shared filesystem (NFS/EFS) — same file on both machines
• File copied before restore
• File re-created empty (process opens, writes from scratch)
Offset mismatch is a non-issue when the file is the same.
Valkey case: Data lives in 100GB of anonymous memory (dumped by CRIU). RDB/AOF are persistence files managed by Valkey — not part of the CRIU FD restore path for live migration.
