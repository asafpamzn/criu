File Offset Mismatch on Restore

What happens when the source file offset doesn't match the replica's file?

Source log at 50KB, replica log already at 100KB:

O_APPEND mode ✅ (most log files)
CRIU restores offset=50KB, but O_APPEND always seeks to end before each write. Process writes at 100KB (end of file).

Safe — offset is effectively ignored for writes. This is why log files opened with O_APPEND just work after migration.
Regular write mode ❌ (no O_APPEND)
CRIU restores offset=50KB. Process writes at 50KB, overwriting existing content in the 50KB–100KB range.

Data corruption if the file diverged between source and replica.
Typical migration pattern ✅
Replica starts fresh from CRIU restore — no pre-existing log file. Either:

• Shared filesystem (NFS/EFS) — same file
• File copied before restore
• File re-created empty

Offset mismatch is a non-issue when the file is identical.
Key takeaway: CRIU faithfully restores the file offset and flags. Whether that's correct depends on your deployment. For live migration with shared storage or fresh replicas, it works perfectly. For diverged files without O_APPEND, beware.
