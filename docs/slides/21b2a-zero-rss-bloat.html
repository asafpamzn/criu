Zero Page RSS Bloat on the Replica

Sending zeros for unmapped pages materializes physical RAM on the replica.

The Problem

What happens on the replica
The replica's page-recv writes every received page via process_vm_writev().

For zero pages, this materializes a physical page filled with zeros. The kernel doesn't know these are "don't care" pages — they consume real RAM.
Scale example
Source RSS 100 GB
Source VMA size 120 GB (VMAs > RSS)
Unmapped holes ~20 GB of zeros sent
Replica RSS ~120 GB (20% bloat)

Why It's Tolerable Today

Self-healing factors
1. jemalloc reclaims zero pages on next allocation cycle
2. Dense Valkey heaps have few unmapped holes (<5%)
3. Replica is temporary — becomes primary soon
4. Alternative (deadlock from skipping) is worse
Current code path 
Source: page unmapped (EFAULT)
  → memset(buf, 0, PAGE_SIZE)
  → send_page_compressed(zero page)
Replica: process_vm_writev(zeros)
  → physical page allocated ❌
For dense heaps (Valkey): bloat is typically a few hundred pages out of 52M (<0.001%). Only sparse allocators with many unmapped holes see significant impact.
