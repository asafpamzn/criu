Hardware Interrupts

Electrical events from hardware — completely invisible to processes.

What they are
Electrical events from hardware: timer tick, disk I/O complete, network packet arrived, keyboard keypress. The CPU stops what it's doing and jumps to a kernel interrupt handler.
Who handles them
The kernel — always. Interrupt handlers run in kernel space with no process context. The interrupted process is simply paused and resumed — it never knows it happened.
Visible to process?
No. Completely transparent. There is no per-process interrupt state. Nothing to checkpoint.

Interrupt Flow

CPU executing process code
        ↓
[INTERRUPT] ← hardware signal (e.g. NIC)
        ↓
Kernel interrupt handler runs
(process is paused, unaware)
        ↓
Handler finishes → CPU resumes process
(process never knew)
Why CRIU ignores interrupts
Interrupt effects that matter to processes are mediated through higher-level abstractions CRIU does save:

• Disk I/O complete → file descriptor state
• Network packet arrived → socket buffers (TCP repair)
• Timer tick → POSIX timers / itimers

Interrupts themselves are transient kernel events — no per-process state to checkpoint.
