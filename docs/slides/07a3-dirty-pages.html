What Are Dirty Pages?

The Dirty Bit — Hardware Level

Every page of memory has a Page Table Entry (PTE) in the CPU's page table. One bit in the PTE is the dirty bit:

Clean Page (dirty=0)
Content matches its source. For file-backed pages: matches the file on disk. For anonymous pages after fork: matches the parent's copy. The kernel can drop clean file pages — just re-read from disk later.
Dirty Page (dirty=1)
The process has written to this page. In-memory content differs from the backing source. For file pages: must be written back to disk before reclaiming. For anonymous pages (heap/stack): data exists only in RAM — losing it means data loss.
Page Table Entry (PTE) on x86_64:
┌─────────────────────────────────┐
│ Physical Address │ Flags        │
│ (bits 12-51)     │ D=dirty      │
│                  │ A=accessed   │
│                  │ R/W=writable │
│                  │ P=present    │
└─────────────────────────────────┘
CPU sets the D bit automatically
on first write — no software needed.

Why CRIU Cares About Dirty Pages

What must be dumped?
Clean file-backed pages → skip (re-read from file on restore)
Dirty file-backed pages → MUST dump (modified, differs from file)
Anonymous pages → MUST dump (no backing file at all)

A 100GB Valkey process is mostly anonymous heap → nearly all pages must be dumped.
Iterative Pre-dump (standard CRIU)
Round 1: Dump ALL pages, clear dirty bits
Round 2: Dump only pages dirtied since round 1
Round 3: Even fewer dirty pages...
Final dump: Freeze + dump remaining dirty pages

Each round transfers less data → shorter final freeze.
CLONE Mode Alternative
Instead of querying kernel dirty bits, CLONE mode uses userfaultfd write-protect. Every VMA is write-protected; on first write the CPU traps, CRIU snapshots the original page, then allows the write. Real-time tracking — no page table walk needed.
