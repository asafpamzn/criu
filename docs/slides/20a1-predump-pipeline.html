Pre-dump: The Freeze Pipeline

The process is FROZEN for the entire duration of this pipeline.

① SEIZE
Freeze threads
→
② smaps
Parse VMAs
→
③ Infect
Inject parasite
→
④ PAGEMAP ★
The expensive part
→
⑤ drain
Read pages
→
⑥ clear_refs
Reset dirty bits
→
⑦ UNFREEZE
Resume process

The Call Chain

pre_dump_one_task()
  collect_mappings(pid, &vmas, NULL)
  parasite_infect_seized(pid, item, &vmas)
  parasite_dump_pages_seized(item, &vmas, &mdc, ctl)
    __parasite_dump_pages_seized()
      pmc_init()           // open /proc/PID/pagemap
      for each VMA:
        generate_vma_iovs()
          pmc_get_map()    // ★ read pagemap
          generate_iovs()  // ★ page-by-page loop
      drain_pages()        // read page contents
      task_reset_dirty_track() // clear_refs
  compel_cure_remote()     // remove parasite

Why the freeze is long

Step ④ dominates
200GB Valkey = 52M pages. Even with PAGEMAP_SCAN, the kernel walks all page tables. On first pre-dump ALL pages are dirty → all 52M classified.
Result: multi-second freeze
Pagemap scan ≈ 2-5s, drain ≈ varies. The process is completely unresponsive. Unacceptable for production Valkey.
