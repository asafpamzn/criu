Migrating TCP Connections Across Machines

CRIU can restore TCP state perfectly — but the IP address changes.

The Problem: TCP 4-Tuple

A TCP connection is identified by
(src_ip, src_port, dst_ip, dst_port)

Client connected to: 10.0.1.5:6379
After migration, server is at: 10.0.2.8:6379

CRIU restores the socket with TCP_REPAIR: seq numbers ✅, queued data ✅, window ✅.
But the server IP changed. The client's OS routes packets to 10.0.1.5 — which is now dead. Connection hangs → timeout → error.

What Must the Client Do?

With floating IP (recommended)
Nothing. The IP moves to the new machine. The client's TCP connection continues mid-stream. It sees a brief pause (~50ms) but no disconnection. No code changes needed.
Without floating IP
Reconnect. Client gets a TCP error (RST or timeout), must resolve new IP and reconnect. Well-written clients (Valkey, Redis libraries) do this automatically with retry logic.

Solutions for Seamless Migration

1. Floating IP / VIP ✅ Best
Move the IP address to the new machine:
• AWS: Reassign ENI (Elastic Network Interface) or secondary private IP
• On-prem: ARP gratuitous announcement (keepalived/VRRP)
• GCP: Alias IP range move

Same IP appears on new host → all existing connections continue via TCP_REPAIR
2. DNS Update (reconnect needed)
Update DNS record to point to new IP. Short TTL (e.g., 10s) means clients pick up change quickly. But existing connections must reconnect.
3. Load Balancer / Proxy
Client → NLB/HAProxy → backend. Move backend routing rule. New connections go to new host. Existing connections through the proxy need the proxy to handle the switch (NLB can do this with target group deregistration + re-registration).
For Valkey live migration: We use floating IP (ENI migration in AWS). The client sees a ~50ms pause, zero disconnections, zero data loss. CRIU's TCP_REPAIR ensures the TCP state is preserved byte-perfectly.
